# ADR 0002：采用内置 ToolProvider 模块，而非运行时插件系统

- 状态：已由 [ADR 0008](0008-microkernel-sidecar-plugins.md) 部分取代（演进为微内核 + 进程外 Sidecar 插件架构）
- 日期：2026-10-18
- 关联：[架构总览](../architecture.md)、[V1 详细设计](../superpowers/specs/2026-10-18-dontstool-design.md)、[ADR 0008](0008-microkernel-sidecar-plugins.md)

## 背景

项目最初希望拥有“插件化架构”。在澄清需求后，约束如下：

- 个人自用，工具作者基本只有项目作者本人。
- V1 工具数量有限（应用/文件搜索、文本工具、网页搜索、翻译）。
- 没有第三方插件市场、热插拔、租户隔离或跨语言插件的现实需求。
- 主要目标是尽快得到一个原生、流畅、可维护的启动器。

运行时要实现的能力包括：插件发现、manifest、进程生命周期、JSON-RPC/UI 协议、错误与超时、UI 声明式渲染等。这些成本在 V1 无法带来对应的用户价值。

## 决策

采用 **编译期内置模块** 作为 V1 的扩展模型：

- 所有工具实现统一的 `ToolProvider` 协议。
- `ToolRegistry` 在启动时注册内置 Provider。
- 搜索核心只依赖协议，不依赖具体工具。
- 新增工具 = 新增 Swift 文件并注册 + 重新编译 App。

V1 不实现：

- 运行时加载插件
- 插件市场
- 进程外插件
- 动态 Swift Bundle

## 被否决的替代方案

1. **进程外 Sidecar 插件**：语言无关、可隔离崩溃、可热插拔；但协议、进程管理、UI 渲染、调试成本高，V1 不需要。
2. **进程内动态 Swift Bundle**：可用原生 UI、无需重编主程序；但 ABI/签名/崩溃隔离复杂，收益低于成本。
3. **直接引入 WebView 插件运行时**：与项目追求的原生体验相悖。

## 后果

正面：

- 无 IPC、无序列化、无进程管理，性能与调试体验最好。
- 类型安全，Provider 可以直接使用 Swift 并发与系统框架。
- 代码结构清晰，新增工具只需要改一个注册点。
- 可以把精力集中在搜索质量、交互和系统集成上。

负面：

- 新增或修改工具必须重新编译并重启 App。
- 不能加载第三方或用其他语言编写的工具。
- Provider 与主程序同生命周期，崩溃会影响整个 App。

## 何时重新考虑

出现以下任一情况时，新增 ADR 并评估 Sidecar 架构：

- 需要在主程序不重新编译的情况下安装/更新工具。
- 需要第三方开发者编写工具。
- 需要其他语言实现工具。
- 需要崩溃隔离或工具级权限控制。
- 工具数量与复杂度增长到内置模块难以维护。

`ToolProvider` 协议就是为这一演进预留的边界：未来的 `SidecarProvider` 可以实现同一个协议，把请求转发给子进程，上层搜索流程无需变化。
